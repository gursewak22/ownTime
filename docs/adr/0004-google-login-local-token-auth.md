# ADR-0004: Google Login with a Local Token Auth Layer

**Status:** Accepted — decisions #5, #8, and the HS256 half of #3 superseded by
[ADR-0005](0005-harden-auth-for-public-internet.md) for public-internet, separately
deployed operation

**Date:** 2026-07-07

**Author(s):** gursewak22 (with Claude Code)

---

### Context

ADR 0001 (decisions #9 and #12) deliberately shipped the backend with no real
authentication: identity arrived as a spoofable `x-user-id` header, on the
promise that real auth would later touch only the `@CurrentUser()` decorator and
the `User` model. This ADR executes that swap.

The product's primary deployment is a **single modular-monolith backend on a LAN,
often over plain HTTP**, used by a small, known set of people. There is no second
service that needs to verify tokens, and no role model — access control is just
"is this a known user" plus per-user data scoping. That threat model, not a
public multi-tenant SaaS, is what these decisions optimize for.

**Quality attributes in play:**

- **Security (integrity):** a client must not be able to forge identity or tamper
  with a token offline; credentials at rest (in the DB) must not be replayable if
  leaked.
- **Availability / offline-resilience:** authenticating a request must not depend
  on the public internet. A LAN box with a cold WAN link must still serve
  authenticated traffic.
- **Performance (per-request latency):** authentication runs on *every* request,
  so its steady-state cost must be near zero.
- **Operability / simplicity:** three endpoints and one guard should not require a
  strategy framework or a second network service to operate.
- **Deployability:** the plain-HTTP LAN mode must keep working, and local dev must
  run without any Google credentials at all.

**Quality attribute scenario:** During a normal authenticated request, while the
host has **no internet connectivity**, when a client presents a valid access
token, the system must authorize the request and populate `req.user` with **zero
network calls and zero database reads** before the route handler runs.

### Decision

**Users authenticate once with a Google ID token that the backend verifies
locally; the monolith then issues and verifies its own stateless HS256 access
token (15m) plus an opaque, hashed, rotating refresh token (30d), enforced by a
single global `AuthGuard` that reads nothing but the token.**

Decision detail (each row is elaborated or defended under *Alternatives*):

| #  | Area                | Decision                                                                     |
|----|---------------------|------------------------------------------------------------------------------|
| 1  | Login method        | Google Identity Services ID token — the only login method                    |
| 2  | Google verification | `google-auth-library` `verifyIdToken` — local check against cached certs     |
| 3  | Access token        | Self-issued HS256 JWT (`@nestjs/jwt`), claim `{ sub: User.id }`, TTL 15m      |
| 4  | Refresh token       | Opaque 256-bit random, SHA-256-hashed in `RefreshToken`, TTL 30d             |
| 5  | Rotation            | Rotate on every refresh, with a **60s reuse-grace window** (only ever shrunk) |
| 6  | Enforcement         | One global `APP_GUARD` (`AuthGuard`) + method-level `@Public()` opt-outs      |
| 7  | Seam contract       | `@CurrentUser()` reads `req.user` set by the guard; zero service-code changes |
| 8  | Frontend storage    | Access token in memory; refresh token + profile in `localStorage`            |
| 9  | Dev fallback        | `x-user-id` header behind `AUTH_ALLOW_DEV_HEADER` **and** non-production env  |
| 10 | User model          | `googleSub` (unique), `email`, `name`, `picture` — all nullable              |

### Alternatives Considered

**Alternative 1: Verify Google ID tokens via Google's `tokeninfo` endpoint**
- Description: on each login, call `https://oauth2.googleapis.com/tokeninfo`
  instead of verifying the signature locally.
- Why rejected: puts the public internet on the hot path of authentication.
  Sacrifices **availability/offline-resilience** — the exact property the QA
  scenario protects. Local `verifyIdToken` fetches Google's signing certs once,
  caches them in memory, and touches the network only when that cache is cold.

**Alternative 2: passport / `@nestjs/passport` strategy framework**
- Description: model login as a passport strategy with guards generated by the
  framework.
- Why rejected: three endpoints and one guard don't justify the abstraction.
  Sacrifices **operability/simplicity** for indirection we would have to learn and
  maintain, with no capability gained.

**Alternative 3: RS256 access tokens with a JWKS endpoint**
- Description: sign access tokens with an asymmetric key and publish public keys
  so any party can verify.
- Why rejected: today the monolith is both the sole issuer and the sole verifier,
  so a shared local secret (`AUTH_JWT_SECRET`) verifies fully in-process. RS256
  buys multi-verifier trust we don't have a second consumer for, at the cost of
  key management. Sacrifices **operability/simplicity** now for **extensibility**
  we've deferred (see Revisit triggers). Boot refuses a missing secret and
  refuses the checked-in placeholder when `NODE_ENV=production`.

**Alternative 4: Server-side (stateful) sessions**
- Description: store a session server-side and look it up on every request.
- Why rejected: a DB read on *every* request. Sacrifices **per-request
  performance** — and the QA scenario's "zero DB reads" — for a revocation
  immediacy the LAN threat model doesn't require. Stateless JWTs make the guard
  free at the cost of not being able to revoke an outstanding access token
  (bounded to ≤15m; see Consequences).

**Alternative 5: `httpOnly; Secure` cookies for the refresh token**
- Description: hold the refresh token in a cookie the JS can't read, immune to
  XSS exfiltration.
- Why rejected: cross-origin cookies require `SameSite=None; Secure`, i.e. HTTPS,
  which breaks the plain-HTTP LAN deployment. Sacrifices **deployability** in the
  primary environment. It also would split the auth seam, whereas keeping the
  token in the store keeps `api-client.ts` the *only* place credentials are
  attached. Accepted cost: the token is XSS-readable (see Consequences).

### Consequences

**Positive:**
- (+) **Per-request auth is genuinely free** — the guard's steady state is a
  single in-process `jwt.verifyAsync`: no DB read, no network. This is the core
  performance and offline-resilience win, and it satisfies the QA scenario.
- (+) **Integrity at rest** — refresh tokens are opaque and stored only as SHA-256
  hashes with `onDelete: Cascade`, so a `RefreshToken` table leak yields nothing
  replayable.
- (+) **Rotation is safe under races** — the 60s grace window only ever *shrinks*
  the old token's `expiresAt`, so a lost response or a second tab holding the
  stale token recovers instead of being force-logged-out, and a replay inside the
  window cannot keep extending its own life.
- (+) **Seam preserved exactly as ADR 0001 promised** — the global `APP_GUARD`
  populates `req.user` before pipes/param decorators run (including ahead of
  multer on the scribe upload route); no controller or service code changed.
  `@Public()` is applied per method, not per class, so a future `/auth/me` can't
  accidentally ship unauthenticated.
- (+) **Safe to expose on the LAN** once `AUTH_ALLOW_DEV_HEADER=false`; the
  spoofable header is double-gated (env flag **and** `NODE_ENV !== 'production'`),
  so a copied `.env` alone can never reopen the hole in production.

**Negative (deliberate trade-offs for the LAN threat model):**
- (-) **No revocation of outstanding access tokens.** Logout deletes the refresh
  row but the access token stays valid for its ≤15m TTL — inherent to stateless
  JWTs, and the direct cost of rejecting Alternative 4.
- (-) **No refresh-reuse theft detection / token-family revocation.** Rotation is
  purely time-based (no `used`/`rotatedAt` flag). A stolen refresh token and the
  legitimate client can *both* keep minting valid sessions indefinitely; nothing
  detects the fork. This is the largest accepted security gap.
- (-) **The `localStorage` refresh token is readable by XSS** — the cost of
  rejecting Alternative 5. Mitigated (not eliminated) by the short access TTL and
  strict same-origin discipline.
- (-) **No rate limiting on `/auth/*`.** `/auth/refresh` is protected by 256-bit
  token entropy, but `/auth/google` will verify unbounded submissions. Acceptable
  only because the surface is a trusted LAN.
- (-) **Refresh has write amplification** — every `issueSession` does three DB
  round-trips (`create` the new token, an opportunistic user-scoped `deleteMany`
  sweep of expired rows, and a `findUniqueOrThrow` for the profile). Cheap at this
  scale (all user-scoped, indexed) and it runs only ~every 15m per client, but it
  is not free the way the access-token path is.

**Neutral / Risks:**
- The very first Google login needs internet to warm Google's cert cache; after
  that the auth path has no internet dependency. Each process/replica keeps its
  own cert cache — a non-issue at monolith scale, a consideration if we ever
  scale out.
- Expired-row cleanup is opportunistic (piggybacked on session issue), not a
  scheduled job. Abandoned users who never log in again leave rows until their
  next session that never comes; harmless but unbounded in the pathological case.

### Revisit triggers

- **A second backend service needs to verify tokens** → switch to RS256 + a JWKS
  endpoint (Alternative 3); the auth layer becomes its own network service.
- **Roles, sharing, or cross-user access** → add an authorization layer on top of
  the identity guard.
- **Any public-internet exposure** → HTTPS everywhere, rate limiting on
  `/auth/*`, refresh-reuse detection with token-family revocation, and reconsider
  `httpOnly` cookies (Alternative 5) before flipping the switch.
